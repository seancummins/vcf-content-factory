## Security conclusions

1. **Exact-empty is evidence based and narrowly scoped.** Actual SDK `ResourceKindIdentifiers` synchronization can produce exact empty strings for absent optional fields. The dispatcher directly validates delivered identifier keys/duplicates/uniqueness before interpreting mode; it does not invoke that synchronizer, erase unknown fields, fix flags, trim, case-fold or mutate the carrier. Absence and exact `fixture` preserve their prior behavior; only exact empty gains the validated fixture route. Raw present-null still returns `EXECUTION_MODE_NULL`, and whitespace/unknown/case variants reject.
2. **Fixture content is a positive discriminator.** Empty mode alone is insufficient. The strict existing fixture parser must accept exactly one bounded complete fixture; every known diagnostic field must be absent/null/exact empty. Literal `false` diagnostic flags remain populated and reject fixture selection. Explicit `read_only_diagnostic` remains the sole diagnostic route and failed diagnostic validation has no fixture fallback.
3. **Associated credentials remain fail closed.** Any nonnull associated target `CredentialConfig`, including an empty/invalid object, rejects all fixture forms without reading/decrypting it. For the new empty-mode form, any nonnull `credentialUuid` reference also rejects. Historical absence/exact-fixture UUID-reference behavior is deliberately preserved rather than silently changed. The empty-mode stamp records that reference so an in-place association added after acceptance retires the configuration before publication.
4. **Ownership and latches remain.** The exact public boxed-Integer collector constructor is retained and lazily forwards the original SDK initialization arguments. Collector ID, mode and configured instance latches remain. A latched diagnostic cannot switch to fixture by clearing mode. Invalid reconfiguration retires rather than falling back. Pre/post fixture callbacks retain the raw full-source mutation fence; fixture deltas retain the same-owner/current-session checks and reject diagnostic/credential/custom/extended deltas.
5. **No diagnostic publication path added.** The diagnostic direct-interface path still never constructs the publishing fixture `AdapterBase`. It returns fresh empty actual SDK collect/discovery payloads; empty per-resource result maps/embedded discovery/resource-status maps preclude resource metrics, properties, events, resources and relationships. Sanitized adapter status/counts remain intentional. Existing generation/cancellation/one-shot isolation is unchanged.
6. **TLS/credential/native boundaries unchanged.** No endpoint, trust manager, hostname/date enforcement, certificate delivery, credential acquisition/decryption, transport, token, source inventory or relationship code changed. No fallback credential, dummy association, external process/Python/container/array dependency, network action or download is introduced. The raw carrier is preserved, and rejection messages still use only the fixed enum reason set, without input values, exception text, class names, credentials or causes.
